# Decisions

One line per non-obvious choice, newest last.

- Phase 0: pnpm workspace uses `tsc -b` project references across `packages/*`; `fixtures/demo-frontend` is typechecked separately (`tsc --noEmit`, bundler resolution, React JSX) and is deliberately excluded from the root reference graph since it's a fixture, not a library.
- Phase 0: `fixtures/demo-frontend`'s generated-codegen-style API (`src/api/generatedApi.ts`) is hand-authored to match the shape of real `@rtk-query/codegen-openapi` output (`injectEndpoints`, operationId-keyed builders) rather than produced by actually running the codegen tool, to keep the fixture deterministic and offline-friendly.
- Phase 0: `fixtures/specs/head-*.yaml` are hand-verified valid OpenAPI documents, one per `ChangeKind`, each a full copy of `v1.yaml` with exactly one targeted change. `oasdiff` isn't installed/exercised yet — that starts Phase 1.
- Phase 0: pnpm is invoked via `corepack pnpm` rather than a global `pnpm` binary, because `corepack enable`'s symlink step needs root on this machine.

## Phase 1A: spec-diff / oasdiff

- `oasdiff` v1.32.1 is vendored at `.tools/oasdiff` (gitignored) — no brew/go available on this machine to install it properly. `packages/spec-diff/src/oasdiffClient.ts` resolves the binary via `OASDIFF_BIN` env var, falling back to `oasdiff` on `PATH`; a real dev machine/CI should install oasdiff normally and rely on the PATH fallback. `vitest.config.ts` sets `OASDIFF_BIN` to the vendored path so tests are self-contained here.
- We use `oasdiff changelog <base> <revision> -f json`, not `breaking` or `diff`: `changelog` is the only command that reports every change (breaking and non-breaking) with a stable per-change `id`, which is what we need to build a ChangeKind mapping. Confirmed shape via `oasdiff schema` (JSON Schema for `--format json`, `additionalProperties: false`): `{id, text, level, operation?, operationId?, path?, section?, baseSource?, revisionSource?, fingerprint?}`. No dedicated field for the exact property path that changed — it's embedded in `text` only.
- `SpecChange.breaking = (oasdiff level >= 2)`, not `level === 3`. Verified empirically: running oasdiff's own `breaking` command on our `request-field-removed` fixture (`request-property-removed`, level 2/WARN) includes it in the breaking-changes output; running it on `enum-value-removed` (level 1/INFO) returns `[]`. So oasdiff's own breaking threshold is WARN-or-above, and we mirror that rather than inventing our own threshold.
- **oasdiff id → ChangeKind mapping** (the full table; `text` regexes live in `normalize.ts`'s `FIELD_EXTRACTORS`):

  | oasdiff id | ChangeKind | notes |
  |---|---|---|
  | `api-path-removed-without-deprecation` | `endpoint-removed` (or correlated into `method-changed`/`path-changed`, see below) | whole path removed |
  | `api-removed-without-deprecation` | `endpoint-removed` (or correlated, see below) | one operation removed from a path that may still have other methods |
  | `response-required-property-removed` | `response-field-removed` | |
  | `response-property-type-changed` | `response-field-type-changed` | |
  | `response-property-became-optional` | `response-field-became-optional` | |
  | `response-property-enum-value-removed` | `enum-value-removed` | level 1/INFO in practice — narrows the response, not breaking |
  | `new-required-request-property` | `request-field-added-required` | |
  | `request-property-removed` | `request-field-removed` | level 2/WARN in practice, still `breaking: true` per the rule above |
  | `new-required-request-parameter` | `param-added-required` | |

- **`method-changed`/`path-changed` have no dedicated oasdiff id.** oasdiff always represents "the same operation moved" as a removal (one of the two ids above) plus a separate, non-breaking `endpoint-added` for the new shape. `normalize.ts` correlates a removal and an `endpoint-added` when they share the same non-empty `operationId`: same path + different method → `method-changed`; same method + different path → `path-changed`; both differ (not exercised by any fixture — genuinely ambiguous) → falls back to reporting the removal alone as `endpoint-removed` rather than guessing. A removal with no correlated addition → `endpoint-removed`. An `endpoint-added` with no correlated removal is a genuinely new endpoint and is silently ignored (see below) — nothing in an existing frontend can depend on an endpoint that didn't exist before.
- **Ignored vs. unmapped — two different buckets, not one.** "Unmapped" (per the task's requirement 4) means an oasdiff id we don't recognize at all — those are always pushed to the `unmapped` array, never dropped. Separately, there's a small **ignore-list** (`api-major-version-not-bumped`, and a `endpoint-added` that didn't correlate to any removal) of ids we *do* recognize but that aren't API-surface changes at all: `api-major-version-not-bumped` has no `operation`/`path`/`operationId` (it's a semver-hygiene notice about the diff itself, not a `SpecChange` — `SpecChange.method`/`.path` are required fields, so it couldn't be represented even if we wanted to), and a non-correlated `endpoint-added` describes a new capability, not a break. Both are filtered out deliberately and documented here rather than silently vanishing into "unmapped" alongside genuinely-unrecognized ids.
- **fieldPath format**: `<request|response>.<status-or-param-location>.<dotted.path>`, with array-typed segments (oasdiff's `items` path segment) rendered as `[]` attached to the preceding segment (e.g. oasdiff's `users/items/role` → `response.200.users[].role`; a top-level array response's `items/published` → `response.200.[].published`). Request-body fields: `request.body.<field>` (e.g. `request.body.title`). Request parameters: `request.<location>.<name>` (e.g. `request.query.authorId`), where `<location>` is oasdiff's own parameter location string (`query`, `path`, `header`, ...).
- Field-path extraction is regex-based against oasdiff's fixed `text` templates (there's no structured field for it) and is anchored to the exact v1.32.1 wording confirmed against real fixture runs. If a future oasdiff version rewords a message, the regex simply fails to match and the raw change falls through to `unmapped` (visible, not silently wrong) rather than producing an incorrect fieldPath.

## Phase 1B: fe-index / ts-morph

- **ts-morph 28.0.0's types live at `lib/ts-morph.d.ts`, not `dist/`** (`package.json`'s `"types"` field points there) — unusual for this version, worth knowing if a future upgrade changes the layout again.
- **Hook calls are resolved by identifier text, matched globally against all discovered endpoints' hook names — not by import/symbol resolution.** i.e. seeing a call to `useGetUserQuery` anywhere in the project is treated as a call to whichever endpoint named `getUser` produced that hook name, without verifying the call site actually imported it from the right module. This assumes hook names are unique across the whole indexed repo, which holds for RTK Query's naming convention (`use<Key>Query`/`use<Key>Mutation`) and for demo-frontend. It trades a small false-positive risk (an unrelated same-named function elsewhere) for not having to do full cross-file symbol resolution, which is a lot more machinery for a repo-indexing pass. Revisit if this proves too permissive on a real repo.
- **Codegen-vs-hand-written detection**: an endpoint's generic type arguments are checked against the *exact* `@rtk-query/codegen-openapi` naming convention (`<Key>ApiResponse`/`<Key>ApiArg`, e.g. `getUsers` → `GetUsersApiResponse`/`GetUsersApiArg`) — confirmed against the Phase 0 fixture, which was itself hand-authored to match real codegen output. Only when this matches exactly do we trust the endpoint key as a real OpenAPI `operationId`; otherwise (hand-written endpoints) no `operationId` is set at all, so Phase 2 falls back to method+path matching rather than being handed a made-up operationId that doesn't exist in the spec. This is why `getUser` (key chosen by the dev, unrelated to the spec's real `getUserById` operationId) correctly gets no `operationId`, while `getUsers`/`getPost`/`createPost` do.
- **Custom wrapper hooks** (e.g. `useCurrentUser` wrapping `useGetUserQuery`): discovered by scanning every function declaration and arrow-function-valued `const` in the project for a call to an already-known hook anywhere in its body (`discoverWrapperHooks`, a "Pass A.5" that runs after endpoint discovery, before usage-site scanning). Any call site of such a wrapper gets `confidence: 'possible'` unconditionally — for the call site itself and for every field subsequently read off its result — since we can't verify the wrapper didn't reshape, filter, or rename fields along the way. Only one level of wrapping is resolved (matches the fixture); nested wrappers-of-wrappers aren't attempted.
- **`FeUsageSite.confidence` downgrades to `'possible'` in exactly three situations**, matching the task's "never skip, always mark possible" requirement: (1) the value flows through a custom wrapper hook (above), (2) the value is spread (`{...x}` as a JSX spread attribute, or a plain object/array spread) rather than read field-by-field, (3) the destructured `data` (or the relevant tuple/prop binding) is typed `any` per `Node.getType().isAny()` — e.g. an endpoint whose response type wasn't declared. Once a trace starts as `'possible'` it stays `'possible'` for everything downstream of it; a good chain never gets "upgraded" back to `'exact'`.
- **Field-access tracing** (`traceScope`/`classifyIdentifierUse` in `usageSites.ts`) walks every occurrence of a tracked local binding via `forEachDescendant` and builds the full property-access chain (e.g. `data.user.email`), regardless of how deeply it's nested inside conditionals (`data && data.post.published`) or JSX (`{data.post.title}`) — the AST nesting doesn't matter since we're searching for the identifier itself, not pattern-matching a specific statement shape. `.map()`/`.flatMap()` calls on a tracked value are followed one level into the callback, with the array-ness represented as `[]` appended to the chain (e.g. `posts[].id`); a direct child-prop pass-through (`<Child prop={data.user} />`, one level, matching rule 4) resolves the imported component and recurses into its matching destructured parameter, carrying the accumulated symbol forward (e.g. `UserCard`'s own `user.email` read is recorded as `data.user.email`, not just `user.email`) so `UsageSite.symbol` stays meaningful relative to the response root.
- **`api.endpoints.<key>.<accessor>(...)`** (matching rule 3's `initiate`/`select`) is recognized structurally by property-access shape (`X.endpoints.<key>.<accessor>`, where `<key>` matches a known endpoint name) rather than resolving which variable `X` actually is. It's recorded as a `hook-call` site (`confidence: 'exact'`) but we don't attempt to trace field access through its result (`initiate` returns a thunk, `select` returns a selector function to be called elsewhere) — that would require modeling thunks/selectors, out of scope for an MVP indexer.
- **`useLazyXQuery` and mutation hooks share the same `[trigger, state]` tuple shape** (a mutation's state can include `data` too, once the mutation resolves) — handled by one code path: the array pattern's first element is treated as a callable trigger (usage sites recorded as `mutation-arg`, reused for lazy-query triggers too since there's no separate `UsageSite.kind` for "trigger call"), the second element's `data` property (if object-destructured) is traced exactly like a direct query's `data`.
- **Stories are attributed to endpoints indirectly**: a story file importing component `X` is credited to every endpoint that has *any* usage site whose `file` is the file defining `X` — not by statically resolving which endpoint(s) `X`'s own JSX actually renders. This is why `UserCard.stories.tsx` correctly shows up under the `getUser` endpoint (via the child-prop pass-through recording sites in `UserCard.tsx`) without fe-index needing a separate "which endpoints does this component touch" pass.
- **`useLazyXQuery`, `api.endpoints.x.initiate/select`, and the any-typed-response case are covered by small in-memory virtual-source unit tests (`patterns.test.ts`, `project.createSourceFile` with `useInMemoryFileSystem: true`), not by extending `fixtures/demo-frontend`.** MANIFEST.md documents itself as something "later golden tests will rely on" — treated as stable once Phase 0 fixed it, rather than re-churned for every new pattern fe-index needs to cover. One wrinkle specific to the in-memory setup: `@reduxjs/toolkit` isn't resolvable there, so `createApi`'s own (unresolved-import) return type is `any`, which would make every hook's `data` look any-typed regardless of the endpoint's real generics. The lazy-query and any-type test fixtures work around this by hand-declaring the hook function signatures directly (`declare function useXQuery(): {...}`) rather than relying on type inference through `createApi`'s return value — Pass A's structural `createApi`/`builder.query` detection is unaffected either way, since it never looks at hook signatures.
- **Performance harness**: `scripts/generate-synthetic-repo.mjs` writes a synthetic repo (default 500 components, 20 endpoints) to `packages/fe-index/.synthetic-repo/` (gitignored, generated on demand by `scripts/bench.mjs` if missing) rather than an in-memory project, so the benchmark includes real tsconfig/file-system resolution overhead, not just AST-walk time. Measured: ~600ms end-to-end for 500 files against the 20s budget.
