# Decisions

One line per non-obvious choice, newest last.

- Phase 0: pnpm workspace uses `tsc -b` project references across `packages/*`; `fixtures/demo-frontend` is typechecked separately (`tsc --noEmit`, bundler resolution, React JSX) and is deliberately excluded from the root reference graph since it's a fixture, not a library.
- Phase 0: `fixtures/demo-frontend`'s generated-codegen-style API (`src/api/generatedApi.ts`) is hand-authored to match the shape of real `@rtk-query/codegen-openapi` output (`injectEndpoints`, operationId-keyed builders) rather than produced by actually running the codegen tool, to keep the fixture deterministic and offline-friendly.
- Phase 0: `fixtures/specs/head-*.yaml` are hand-verified valid OpenAPI documents, one per `ChangeKind`, each a full copy of `v1.yaml` with exactly one targeted change. `oasdiff` isn't installed/exercised yet — that starts Phase 1.
- Phase 0: pnpm is invoked via `corepack pnpm` rather than a global `pnpm` binary, because `corepack enable`'s symlink step needs root on this machine.

## Phase 1A: spec-diff / oasdiff

- `oasdiff` v1.32.1 is vendored at `.tools/oasdiff` (gitignored) — no brew/go available on this machine to install it properly. `packages/spec-diff/src/oasdiffClient.ts` resolves the binary via `OASDIFF_BIN` env var, falling back to `oasdiff` on `PATH`; a real dev machine/CI should install oasdiff normally and rely on the PATH fallback. `vitest.config.ts` sets `OASDIFF_BIN` to the vendored path so tests are self-contained here.
- We use `oasdiff changelog <base> <revision> -f json`, not `breaking` or `diff`: `changelog` is the only command that reports every change (breaking and non-breaking) with a stable per-change `id`, which is what we need to build a ChangeKind mapping. Confirmed shape via `oasdiff schema` (JSON Schema for `--format json`, `additionalProperties: false`): `{id, text, level, operation?, operationId?, path?, section?, baseSource?, revisionSource?, fingerprint?}`. No dedicated field for the exact property path that changed — it's embedded in `text` only.
- `SpecChange.breaking = (oasdiff level >= 2)`, not `level === 3`. Verified empirically: running oasdiff's own `breaking` command on our `request-field-removed` fixture (`request-property-removed`, level 2/WARN) includes it in the breaking-changes output; running it on `enum-value-removed` (level 1/INFO) returns `[]`. So oasdiff's own breaking threshold is WARN-or-above, and we mirror that rather than inventing our own threshold.
- **oasdiff id → ChangeKind mapping** (the full table; `text` regexes live in `normalize.ts`'s `FIELD_EXTRACTORS`):

  | oasdiff id | ChangeKind | notes |
  |---|---|---|
  | `api-path-removed-without-deprecation` | `endpoint-removed` (or correlated into `method-changed`/`path-changed`, see below) | whole path removed |
  | `api-removed-without-deprecation` | `endpoint-removed` (or correlated, see below) | one operation removed from a path that may still have other methods |
  | `response-required-property-removed` | `response-field-removed` | |
  | `response-property-type-changed` | `response-field-type-changed` | |
  | `response-property-became-optional` | `response-field-became-optional` | |
  | `response-property-enum-value-removed` | `enum-value-removed` | level 1/INFO in practice — narrows the response, not breaking |
  | `new-required-request-property` | `request-field-added-required` | |
  | `request-property-removed` | `request-field-removed` | level 2/WARN in practice, still `breaking: true` per the rule above |
  | `new-required-request-parameter` | `param-added-required` | |

- **`method-changed`/`path-changed` have no dedicated oasdiff id.** oasdiff always represents "the same operation moved" as a removal (one of the two ids above) plus a separate, non-breaking `endpoint-added` for the new shape. `normalize.ts` correlates a removal and an `endpoint-added` when they share the same non-empty `operationId`: same path + different method → `method-changed`; same method + different path → `path-changed`; both differ (not exercised by any fixture — genuinely ambiguous) → falls back to reporting the removal alone as `endpoint-removed` rather than guessing. A removal with no correlated addition → `endpoint-removed`. An `endpoint-added` with no correlated removal is a genuinely new endpoint and is silently ignored (see below) — nothing in an existing frontend can depend on an endpoint that didn't exist before.
- **Ignored vs. unmapped — two different buckets, not one.** "Unmapped" (per the task's requirement 4) means an oasdiff id we don't recognize at all — those are always pushed to the `unmapped` array, never dropped. Separately, there's a small **ignore-list** (`api-major-version-not-bumped`, and a `endpoint-added` that didn't correlate to any removal) of ids we *do* recognize but that aren't API-surface changes at all: `api-major-version-not-bumped` has no `operation`/`path`/`operationId` (it's a semver-hygiene notice about the diff itself, not a `SpecChange` — `SpecChange.method`/`.path` are required fields, so it couldn't be represented even if we wanted to), and a non-correlated `endpoint-added` describes a new capability, not a break. Both are filtered out deliberately and documented here rather than silently vanishing into "unmapped" alongside genuinely-unrecognized ids.
- **fieldPath format**: `<request|response>.<status-or-param-location>.<dotted.path>`, with array-typed segments (oasdiff's `items` path segment) rendered as `[]` attached to the preceding segment (e.g. oasdiff's `users/items/role` → `response.200.users[].role`; a top-level array response's `items/published` → `response.200.[].published`). Request-body fields: `request.body.<field>` (e.g. `request.body.title`). Request parameters: `request.<location>.<name>` (e.g. `request.query.authorId`), where `<location>` is oasdiff's own parameter location string (`query`, `path`, `header`, ...).
- Field-path extraction is regex-based against oasdiff's fixed `text` templates (there's no structured field for it) and is anchored to the exact v1.32.1 wording confirmed against real fixture runs. If a future oasdiff version rewords a message, the regex simply fails to match and the raw change falls through to `unmapped` (visible, not silently wrong) rather than producing an incorrect fieldPath.

## Phase 1B: fe-index / ts-morph

- **ts-morph 28.0.0's types live at `lib/ts-morph.d.ts`, not `dist/`** (`package.json`'s `"types"` field points there) — unusual for this version, worth knowing if a future upgrade changes the layout again.
- **Hook calls are resolved by identifier text, matched globally against all discovered endpoints' hook names — not by import/symbol resolution.** i.e. seeing a call to `useGetUserQuery` anywhere in the project is treated as a call to whichever endpoint named `getUser` produced that hook name, without verifying the call site actually imported it from the right module. This assumes hook names are unique across the whole indexed repo, which holds for RTK Query's naming convention (`use<Key>Query`/`use<Key>Mutation`) and for demo-frontend. It trades a small false-positive risk (an unrelated same-named function elsewhere) for not having to do full cross-file symbol resolution, which is a lot more machinery for a repo-indexing pass. Revisit if this proves too permissive on a real repo.
- **Codegen-vs-hand-written detection**: an endpoint's generic type arguments are checked against the *exact* `@rtk-query/codegen-openapi` naming convention (`<Key>ApiResponse`/`<Key>ApiArg`, e.g. `getUsers` → `GetUsersApiResponse`/`GetUsersApiArg`) — confirmed against the Phase 0 fixture, which was itself hand-authored to match real codegen output. Only when this matches exactly do we trust the endpoint key as a real OpenAPI `operationId`; otherwise (hand-written endpoints) no `operationId` is set at all, so Phase 2 falls back to method+path matching rather than being handed a made-up operationId that doesn't exist in the spec. This is why `getUser` (key chosen by the dev, unrelated to the spec's real `getUserById` operationId) correctly gets no `operationId`, while `getUsers`/`getPost`/`createPost` do.
- **Custom wrapper hooks** (e.g. `useCurrentUser` wrapping `useGetUserQuery`): discovered by scanning every function declaration and arrow-function-valued `const` in the project for a call to an already-known hook anywhere in its body (`discoverWrapperHooks`, a "Pass A.5" that runs after endpoint discovery, before usage-site scanning). Any call site of such a wrapper gets `confidence: 'possible'` unconditionally — for the call site itself and for every field subsequently read off its result — since we can't verify the wrapper didn't reshape, filter, or rename fields along the way. Only one level of wrapping is resolved (matches the fixture); nested wrappers-of-wrappers aren't attempted.
- **`FeUsageSite.confidence` downgrades to `'possible'` in exactly three situations**, matching the task's "never skip, always mark possible" requirement: (1) the value flows through a custom wrapper hook (above), (2) the value is spread (`{...x}` as a JSX spread attribute, or a plain object/array spread) rather than read field-by-field, (3) the destructured `data` (or the relevant tuple/prop binding) is typed `any` per `Node.getType().isAny()` — e.g. an endpoint whose response type wasn't declared. Once a trace starts as `'possible'` it stays `'possible'` for everything downstream of it; a good chain never gets "upgraded" back to `'exact'`.
- **Field-access tracing** (`traceScope`/`classifyIdentifierUse` in `usageSites.ts`) walks every occurrence of a tracked local binding via `forEachDescendant` and builds the full property-access chain (e.g. `data.user.email`), regardless of how deeply it's nested inside conditionals (`data && data.post.published`) or JSX (`{data.post.title}`) — the AST nesting doesn't matter since we're searching for the identifier itself, not pattern-matching a specific statement shape. `.map()`/`.flatMap()` calls on a tracked value are followed one level into the callback, with the array-ness represented as `[]` appended to the chain (e.g. `posts[].id`); a direct child-prop pass-through (`<Child prop={data.user} />`, one level, matching rule 4) resolves the imported component and recurses into its matching destructured parameter, carrying the accumulated symbol forward (e.g. `UserCard`'s own `user.email` read is recorded as `data.user.email`, not just `user.email`) so `UsageSite.symbol` stays meaningful relative to the response root.
- **`api.endpoints.<key>.<accessor>(...)`** (matching rule 3's `initiate`/`select`) is recognized structurally by property-access shape (`X.endpoints.<key>.<accessor>`, where `<key>` matches a known endpoint name) rather than resolving which variable `X` actually is. It's recorded as a `hook-call` site (`confidence: 'exact'`) but we don't attempt to trace field access through its result (`initiate` returns a thunk, `select` returns a selector function to be called elsewhere) — that would require modeling thunks/selectors, out of scope for an MVP indexer.
- **`useLazyXQuery` and mutation hooks share the same `[trigger, state]` tuple shape** (a mutation's state can include `data` too, once the mutation resolves) — handled by one code path: the array pattern's first element is treated as a callable trigger (usage sites recorded as `mutation-arg`, reused for lazy-query triggers too since there's no separate `UsageSite.kind` for "trigger call"), the second element's `data` property (if object-destructured) is traced exactly like a direct query's `data`.
- **Stories are attributed to endpoints indirectly**: a story file importing component `X` is credited to every endpoint that has *any* usage site whose `file` is the file defining `X` — not by statically resolving which endpoint(s) `X`'s own JSX actually renders. This is why `UserCard.stories.tsx` correctly shows up under the `getUser` endpoint (via the child-prop pass-through recording sites in `UserCard.tsx`) without fe-index needing a separate "which endpoints does this component touch" pass.
- **`useLazyXQuery`, `api.endpoints.x.initiate/select`, and the any-typed-response case are covered by small in-memory virtual-source unit tests (`patterns.test.ts`, `project.createSourceFile` with `useInMemoryFileSystem: true`), not by extending `fixtures/demo-frontend`.** MANIFEST.md documents itself as something "later golden tests will rely on" — treated as stable once Phase 0 fixed it, rather than re-churned for every new pattern fe-index needs to cover. One wrinkle specific to the in-memory setup: `@reduxjs/toolkit` isn't resolvable there, so `createApi`'s own (unresolved-import) return type is `any`, which would make every hook's `data` look any-typed regardless of the endpoint's real generics. The lazy-query and any-type test fixtures work around this by hand-declaring the hook function signatures directly (`declare function useXQuery(): {...}`) rather than relying on type inference through `createApi`'s return value — Pass A's structural `createApi`/`builder.query` detection is unaffected either way, since it never looks at hook signatures.
- **Performance harness**: `scripts/generate-synthetic-repo.mjs` writes a synthetic repo (default 500 components, 20 endpoints) to `packages/fe-index/.synthetic-repo/` (gitignored, generated on demand by `scripts/bench.mjs` if missing) rather than an in-memory project, so the benchmark includes real tsconfig/file-system resolution overhead, not just AST-walk time. Measured: ~600ms end-to-end for 500 files against the 20s budget.

## Phase 2: impact / report / cli

- **Bug fixed from Phase 1A**: `method-changed`/`path-changed` `SpecChange`s now carry the endpoint's OLD (base) method+path, not the new one. They used to report the new shape (e.g. `path-changed`'s fixture reported `/posts/{postId}/full`), but existing frontend code still calls the *old* shape -- that's the identity impact matching needs to find the frontend usage that's about to break. The new shape is still noted in `detail`. The two affected Phase 1A tests were updated to match.
- **Shared-type ownership moved to avoid a circular workspace dependency.** `impact` needs `spec-diff` (for `normalizePathParams`, and to consume `SpecChange[]`) and `fe-index` (to consume `FeIndex`) for matching -- but SPEC.md's "Core types (packages/impact/src/types.ts)" originally put `SpecChange`/`UsageSite` *in* `impact`, which those two packages then had to import back from, forming `impact <-> spec-diff` and `impact <-> fe-index` cycles that `tsc -b`'s project references correctly reject (TS6202). Fix: `ChangeKind`/`SpecChange` now live in `packages/spec-diff/src/types.ts` (spec-diff produces them) and `UsageSite` lives in `packages/fe-index/src/types.ts` (fe-index produces it); `packages/impact/src/types.ts` re-exports both plus its own `Impact` type, so `@blast/impact` remains the one-stop import SPEC.md describes, and the dependency graph is one-directional (`impact` depends on the other two; they depend on nothing package-internal).
- **Impact matching splits `ChangeKind`s into two categories**, checked via an exhaustive `switch` (not a `Set.has` lookup, which doesn't narrow `change.kind` to `never` in a fallback branch -- TS caught this when I first tried it):
  - *Endpoint-identity* kinds (`endpoint-removed`, `method-changed`, `path-changed`, `param-added-required`, `request-field-added-required`, `request-field-removed`) break *any* call to the endpoint, so the Impact's sites are every non-`endpoint-def` site fe-index recorded for it. If the endpoint has zero real usage sites, no Impact is produced (a known-but-uncalled endpoint has no frontend impact).
  - *Field-level* kinds (`response-field-removed`, `response-field-type-changed`, `response-field-became-optional`, `enum-value-removed`) only break code reading the one changed field.
- **Field-level matching uses leaf-name comparison, not full-path string matching.** spec-diff's `fieldPath` (`response.200.users[].role`) and fe-index's site `symbol` (`data.users[].role`) come from completely different generators (oasdiff's schema-path text vs. AST variable tracing) with no guaranteed structural correspondence beyond the field's own name -- root-variable naming differs (`data` vs. a renamed local, or no root at all for the frontend side). Comparing just the last dot-segment (array-suffix `[]` stripped) is robust to that and errs toward over-matching rather than under-matching, consistent with "prefer a false possible over a missed impact."
- **A field-level change with no leaf-name match can still produce a `possible` Impact** if the endpoint has an *opaque container* site -- a spread with no resolvable field name (fe-index records these as e.g. `posts[]`, nothing after it). The changed field could be flowing through that spread; we can't rule it out, so it's flagged `possible` rather than silently concluding no impact. Verified against the real fixtures: `response-field-type-changed` on `Post.published` correctly flags `listPosts` (whose only relationship to `Post` is spreading it into `<PostItem {...post} />`) as `possible`, while `createPost` (a mutation with no field-access sites at all) correctly gets no Impact.
- **A change matching a real, used endpoint but touching no field anyone reads is *not* an Impact and is *not* "unmatched."** E.g. `response-field-removed` on `User.role` matches `getUsers`, `getUserById`, and `updateUser` by operationId/method+path, but only `getUsers`'s frontend usage (`UsersTable.tsx`) actually reads `.role` -- the other two produce zero Impacts, correctly, since nothing in `UserProfile`/`UpdateUserForm` touches that field. "Unmatched" is reserved for changes where *no* endpoint could be found at all.
- **Two different "we couldn't fully resolve this" buckets reach the final report, from two different layers**: `unmatched` (an `impact`-recognized `SpecChange` with no matching frontend endpoint at all) and `unrecognized` (an oasdiff finding `spec-diff` itself never turned into a `SpecChange` -- its own `unmapped` bucket, see the Phase 1A section above). `runAnalyze` threads both through to `buildJsonReport`/`buildMarkdownReport` as separate sections so a reader isn't confused about *why* something wasn't resolved -- a tool gap (`unrecognized`) is a different problem than "your frontend doesn't call this" (`unmatched`).
- **Markdown report layout**: one always-visible summary line; every `exact`-confidence change gets its own `<details>` block (one table per change, per the task's wording -- multiple Impacts sharing the same change, e.g. one field-level change matching several endpoints, are grouped into that one table via a stable `changeKey`); all `possible`-confidence impacts are combined into a single `<details>` "Possible impacts" section with a Change column instead of one block each, since they're lower-priority/needs-review rather than an action item per change; `unmatched` and `unrecognized` are likewise single combined sections. Since `<details>` without `open` renders collapsed (only the `<summary>` line shows), a report with many changes still stays well under the ~60-visible-line target -- verified in `report.test.ts` by literally counting lines outside any `<details>`/`</details>` pair.
- **`breaking`-change counting in the summary line counts *changes*, not impacts** -- a distinct `SpecChange` (by `changeKey`) with `breaking: true`, whether or not it produced any Impact, counted once across both matched and unmatched changes. This is deliberately independent of confidence: a `possible` impact from a breaking change still counts toward "breaking changes," and a breaking change nobody's frontend calls (fully unmatched) still counts too, since it's real API-surface breakage worth knowing about even without a known consumer.
- **CLI arg parsing uses Node's built-in `node:util.parseArgs`**, not a dependency like `commander`/`yargs` -- the flag set (`--base`, `--head`, `--frontend`, `--json`, `--md`) is simple enough not to need one, and SPEC.md says to ask before adding a runtime dependency.
- **`blast analyze` always exits 0 on a successful run**, regardless of how many breaking changes or impacts it found. Turning that into a CI failure (`failOn: breaking | never`) is explicitly a Phase 3 GitHub Action config concern layered on top of this command, not this command's own job.
- **Multiple `--frontend` dirs are indexed separately and their endpoints concatenated** into one combined `FeIndex` before matching (`buildCombinedFeIndex` in `packages/cli/src/analyze.ts`) -- file paths already disambiguate which repo a site came from, so no extra "which repo" bookkeeping is needed. The markdown report's relative-path display (`rootDir`) uses the *first* frontend dir as a best-effort root when there's more than one; paths outside it still render correctly, just with leading `..` segments.
- **Golden-file tests** for `impact` (`packages/impact/test/golden/<kind>.json`) and `report` (`packages/report/test/golden/<kind>.md`) run the *real* pipeline (real oasdiff subprocess, real ts-morph project against `fixtures/demo-frontend`) rather than synthetic Impact fixtures, for all 10 `ChangeKind`s. File paths inside the golden JSON are rewritten relative to the repo root first (`packages/impact/src/testSupport.ts`) so they're portable across machines/CI rather than baking in one machine's absolute path.

## Phase 3: GitHub Action

- **`action/action.yml` is a composite action (shell steps + the existing `blast` CLI), not a JS action.** A JS action would need `@actions/core`/`@actions/github` (or `@octokit/rest`) to read inputs and call the GitHub API -- none of those are in SPEC.md's tech stack, and adding a new runtime dependency needs asking first. The composite action instead uses `gh` (preinstalled on GitHub-hosted runners) for the one GitHub API need (posting/updating the PR comment), and plain Node scripts for everything else.
- **No published npm package -- the action builds `blast` from source every run.** `uses: <org>/api-blast-radius@ref` (or, since `action.yml` lives in a subdirectory, `uses: <org>/api-blast-radius/action@ref`) checks out this repo, and the action's first steps run `pnpm install --frozen-lockfile && pnpm run build` inside that checkout before invoking `packages/cli/dist/index.js` directly. `github.action_path` in that case points at the checked-out `action/` subdirectory, which is why the build step's `working-directory` and the CLI path both go up one level (`${{ github.action_path }}/..`) to reach the repo root. This makes every run slower than a published-package action would be; worth revisiting if that becomes a real problem.
- **`.blastradius.yml` validation lives in a pure, unit-tested module** (`action/src/config.mjs`), separate from the CLI-wrapper script that does file I/O (`action/scripts/parse-config.mjs`) -- every other cross-cutting decision (checkout-directory naming, the sticky-comment find-or-create decision, the fail/no-fail decision) follows the same split, so the actual *logic* has real test coverage even though the surrounding `git`/`gh` CLI calls don't.
- **Base spec extraction uses `git show <base-sha>:<spec-path>`**, not a second checkout -- the workflow's own `actions/checkout` step already has the repo (with `fetch-depth: 0`, which the README's example workflow sets, needed so the base commit's blob is actually present to `git show`).
- **Sticky comment**: a hidden HTML-comment marker (`<!-- blast-radius-report -->`, `action/src/stickyComment.mjs`) identifies "the" bot comment on a PR. `gh api` lists existing issue comments, `findStickyCommentId` picks out the marked one, and the script `PATCH`es it if found or `POST`s a new one otherwise -- so re-running the action on later pushes to the same PR updates in place instead of piling up comments. The comment body is written to a temp file and passed via `gh api`'s `-F field=@file` rather than as an inline CLI argument, to sidestep both shell-escaping and OS argv-length limits on a large report.
- **`oasdiff` is installed by downloading the `linux_amd64` release binary directly** (same GitHub Releases source used to vendor it locally in Phase 1A, pinned to the same v1.32.1), assuming a `ubuntu-latest`-class runner -- the standard default for GitHub-hosted Actions. Documented in the action's README as a current limitation rather than silently failing on another platform.
- **Testing boundary, stated plainly**: `action/src/*.mjs`'s pure logic has real unit tests, and `action/src/localE2E.test.mjs` simulates the *whole* pipeline (parse config -> run `blast analyze` for real -> decide fail/no-fail -> decide create/update-comment) using `fixtures/demo-frontend` and `fixtures/specs` as stand-ins for "an already-checked-out frontend repo" and "the base/head spec git would extract" -- proving every piece of logic the action exercises is correct. What is **not** tested is `action.yml` itself as GitHub Actions YAML, or the real `git clone`/`gh api` calls, since that requires a live GitHub Actions run against a real repo pair to verify faithfully (checkout permissions, PR comment permissions, `github.action_path` resolution, etc. can't be simulated locally with confidence). This is called out again in `action/README.md`'s "Testing status" section rather than claimed as done.

## Phase 4: patcher (first LLM use)

- **`claude-sonnet-5` pricing (for cost logging)**: $3.00/1M input, $15.00/1M output tokens -- confirmed via the `claude-api` skill's live-cached pricing table rather than guessed (the skill also surfaced that Sonnet 5's time-limited intro pricing, $2/$10, already expired as of the date this was written, so the standard rate is what's actually in effect). `packages/patcher/src/pricing.ts` falls back to these same rates for any model name it doesn't recognize (logging *a* cost estimate, clearly attributed to the wrong model's rate card, beats logging nothing) -- only `claude-sonnet-5` itself needs to be exact, since that's SPEC.md's `BLAST_MODEL` default.
- **`diff` (npm package) for unified-diff apply**, not a hand-rolled parser -- flagged to the user before adding since it's a new runtime dependency, approved. `diff@9`'s types live at the package's own `libcjs/index.d.ts` (checked directly rather than assumed); `applyPatch(source, patchText)` returns the patched string or literal `false` on failure to fit, which is exactly the `{applied: boolean}` shape `applyDiff.ts` exposes.
- **Grouping impacts by file** (`groupByFile.ts`) is more than "every site's file": for changes to the endpoint's own call shape (`method-changed`, `path-changed`, `param-added-required`, `request-field-added-required`, `request-field-removed`), the endpoint *definition's* file is included too, since the real fix for e.g. a new required query param is updating the `query:` builder itself, not just its callers. `endpoint-removed` is deliberately excluded from that -- there's no in-place edit to make in a definition for an operation that no longer exists; only consumer sites are patchable. `'endpoint-def'`-kind sites themselves are skipped everywhere (purely informational, not something to "fix").
- **Retry loop is 1 initial attempt + 2 retries (3 total)**, matching "retry max 2 times" literally. A failed attempt's changes are discarded (`git checkout -- . && git clean -fd`) before the next attempt, so every retry's diff applies against the same known-good base rather than stacking on top of a previous bad edit — and so a file that ultimately can't be fixed is left byte-for-byte as it started, not half-patched.
- **One scratch branch per whole run, not per file** (`runPatcher`): each file that verifies gets its own commit on that branch as it succeeds; the draft PR (`pushAndOpenDraftPr`, via `gh` CLI like Phase 3 -- no octokit) opens only after *every* file in the batch has verified, and only if the caller explicitly passes `openPr: true`. A single `needs-human` file blocks the PR for the whole run, per SPEC.md ("open a DRAFT PR ... only if every patch verifies").
- **PR-opening is unit-tested via an injectable `exec` function** (`ExecFileFn` on `pushAndOpenDraftPr`), asserting the exact `git push`/`gh pr create` arguments built -- never exercised against a real git remote or GitHub in tests. Same boundary as Phase 3's sticky-comment posting, and for the same reason: pushing a branch and opening a PR needs a real repo and is not something to do implicitly under test.
- **Fixture-patch verification test uses a real git repo and a real `tsc --noEmit` run**, not a mock -- a throwaway `mkdtemp` copy of `fixtures/demo-frontend` (with `node_modules` *symlinked* from the real fixture rather than reinstalled, to keep the test fast), genuinely `git init`'d and committed, with only the `LlmClient` mocked (`MockLlmClient`, canned diffs built via `diff`'s own `createPatch` so they're guaranteed well-formed). This is what "fixture patches pass verification; the LLM client is mocked in unit tests" means in practice here.
- **The test scenario needed a real, isolated compile break to be meaningful**: initially, removing `role` from the fixture's `User` interface broke `UserCard.stories.tsx` (a hardcoded object literal), not `UsersTable.tsx` -- tsc failed on an unrelated file, and the "verified" test would have passed regardless of whether the patch under test did anything. Fixing Storybook stories is out of scope for the patcher (`Impact.stories` is tracked separately from `Impact.sites`; nothing routes a fix there), so the test's `beforeEach` neutralizes the story fixture's `role` reference directly, isolating the one compile error the test is actually about. Worth remembering for any future fixture-based patcher test: confirm the *specific* file under test genuinely fails verification before the fix and genuinely passes after, don't assume it from the change description alone.

## Phase 5: evals

- **`evals` is a real TypeScript workspace package** (added to `pnpm-workspace.yaml` and the root `tsconfig.json`'s references), not a plain-scripts directory like `action/` -- it needs real imports from `@blast/spec-diff`/`@blast/fe-index`/`@blast/impact`/`@blast/patcher`, which only resolve cleanly as a workspace member.
- **`expected.json`'s ground truth is `(endpoint, kind, confidence)` triples, not full `Impact` objects.** A full `Impact` bakes in oasdiff's own `detail` wording and the complete `sites` array -- both would make a case brittle to an oasdiff version bump or a fe-index internal refactor that changes *how* something is found without changing *whether* it should be found. The triple is the actual claim worth pinning, and it's what a human hand-authoring one of the ~20 additional cases can reasonably produce without needing to run the tool first to copy its exact output shape.
- **The 10 seed cases are generated from work already done, not re-authored**: `evals/scripts/generate-cases-from-fixtures.mjs` derives each case's `expected.json` from `packages/impact/test/golden/<kind>.json` (Phase 2's own hand-verified golden files) rather than re-deriving ground truth by hand a second time. Running `pnpm eval` against these reproduces 100% precision/recall on every case by construction -- that's a sanity check that the eval harness itself is wired correctly (loading cases, running the real pipeline, scoring), not a claim about real-world accuracy. The ~20 cases still to come are what will actually test the matcher against the unknown.
- **Each case's `frontend/` is a real snapshot copy, not a symlink to `fixtures/demo-frontend`** -- deliberately decoupled so a later change to the shared fixture can't silently drift an existing eval baseline. `node_modules` inside each snapshot *is* symlinked back to the real fixture's install (not reinstalled 10 times), since that's just install-time convenience, not part of what the case is pinning.
- **Confidence-bucket scoring is strict and non-overlapping** (`scoring.ts`): a true positive requires the actual confidence to equal the expected confidence exactly. Finding an `exact` impact where `possible` was expected does not count as a `possible`-bucket hit -- it's scored as a `possible`-bucket false negative *and* an `exact`-bucket false positive, since it's a different (stronger) claim than what the case asserts. Alternative designs (treating `exact` as satisfying an expected `possible`) were considered and rejected: they'd hide a matcher becoming *more* confident than a case's ground truth actually justifies, which is exactly the kind of drift an eval suite should catch, not paper over.
- **Aggregate precision/recall is micro-averaged** (confusion-matrix counts summed across all cases first, one precision/recall computed from the sum) rather than macro-averaged (averaging each case's own precision/recall). With a small, uneven number of expected impacts per case -- most of the 10 seed cases have exactly one -- macro-averaging would let a single-impact case's binary hit/miss swing the aggregate as much as a case with several impacts.
- **Patch verification never runs by default** -- `pnpm eval` alone only measures impact precision/recall (no API calls, no cost). Running the real patcher needs an explicit `--with-patches` flag *and* `ANTHROPIC_API_KEY` set; either being absent prints a clear skip reason rather than silently omitting the section or crashing. This was a deliberate choice beyond what SPEC.md's wording strictly required: a key merely being present in the environment (e.g. on a dev's machine, or eventually in CI) is not the same as consenting to spend money every time someone runs `pnpm eval` while iterating on the matcher itself.
- **No live end-to-end run has actually exercised `--with-patches`** -- no `ANTHROPIC_API_KEY` is set in this sandbox (same as Phase 4), so that code path is implemented and structurally consistent with `packages/patcher`'s own tested `runPatcher` orchestration, but hasn't itself been run against a real API call. The plain (`pnpm eval`, no patches) path has been run for real and produces the report shown when this phase was built.
